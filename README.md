# slint — 检查公开文本里的「需求」是不是真的需求

零依赖、单文件、Node 18+。两个工具，一个共同目的：**在你把公开文本统计成数字之前，先证明那些数字不是你自己编的。**

```bash
node slint-community.mjs --days 30     # 社区公开文本 → 真实付费意愿信号
node slint-page.mjs https://example.com https://example.org   # 页面 → AI 引用就绪度
```

两个都是本地跑，不需要 key、不需要账号、不上传任何输入。

---

## 为什么需要它

大多数「我用公开数据找到了一个真实需求」的结论，其实是这么来的：

> 在某社区搜 `"willing to pay"`，命中 367 条，其中大部分提到了具体产品，所以我找到了 367 个买家信号。

这个推论有三处会骗人，而且三处都在同一份数据里。

### 1. 松散匹配 ≠ 精确短语

搜索引擎默认把 `willing to pay` 拆成词 OR 匹配。本项目实测同一个窗口、同一个社区：

| 查询方式 | 命中数 |
|---|---|
| 松散词（不加引号） | 76,722 |
| 精确短语（加引号） | 3,596 |

**差 21 倍。** 而且松散结果的前三条里根本没有那个短语。

`slint-community.mjs` 所有计数强制加引号，并且先跑 canary：

```js
// 不存在的字符串必须返回 0。返回非 0 说明引擎在做别的事，后面所有数字作废。
const canaryHits = await get(ALGOLIA + '?query=zzqx floopernaut grimbly');
if (canaryHits !== 0) process.exit(2);
```

canary 非 0 就直接退出、不输出数字。这是工具里最重要的一行。

### 2. 「我愿意付钱」大多是修辞，不是需求

即使精确命中，逐条读之后会发现大量句子长这样：

> *"If you built a tool that did X, **I'd pay** for it, **but** I already use Y."*

`if / but / although / though / wish` 是修辞信号。本项目 30 天窗口实测：

```
短语命中合计（未去重）  370
去重后                   367
独立作者                 333
含可交付物词              45      ← 提到 dataset / api / csv / database 等"一个可做的东西"
命中修辞标记             266      ← 72.5%
两条都命中（真候选）      11
```

**72.5% 的"付费信号"是修辞。** 再把那 11 条人工逐条读，结论是：全部指向已存在的品类、已死的产品，或「请给现有产品加个功能」——没有一条是新产品的需求。

这个比例不是一次性的巧合。换一个时间窗口重跑，结论复现：

| 窗口 | 抓取时间 | 去重后 | 修辞占比 | 过关候选 |
|---|---|---|---|---|
| 30 天 | 2026-10-08 | 367 | **72.5%** | 11 |
| 7 天 | 2026-10-12 | 85 | **69.4%** | 3 |

7 天窗口跑出来的 3 条候选里，有一条是「有人想要一个在浏览器标签里运行的 Firefox 扩展，**I would pay for this**」——第一人称、无修辞、描述了一个可做的东西。这是三闸门能捞出来的真实信号长什么样，也是它为什么值得跑：捞出东西的窗口和捞不出东西的窗口，用的是同一把尺子。

### 3. 自己的工具只在自己页面上验证过

第 8 个教训，比前两条更根本：

> 工具的判据是**你**写的，页面是**照你的判据**写的。两者独立时才叫验证。

`slint-page.mjs` 就是为这件事写的：把网页版 8 项判据原样移植成 Node（阈值一字不改），然后跑**别人的页面**。

实测 5 个站外真实页面，同一把尺子（抓取时间 2026-10-11，与上表下方 README 数据同源）：

| 页面 | 得分 | 字节 |
|---|---|---|
| the-seo-autopilot.com（英文数据长文） | 8/8 | 788,965 |
| dev.to 长文（英文） | 8/8 | 99,996 |
| CSDN 博客（中文） | 7/8 | 196,472 |
| siwan.io（中文长文） | 6/8 | 49,189 |
| **本项目自己的页面** | **7/8 → 8/8** | 22,046 |

最后一行是重点。它第一次跑在自己页面上时是 **7/8**，抓出的失败项是 check 5「主题簇内链数不足」。修掉之后同一个工具再跑，变成 8/8。

**这就是自证偏差的具体形态**：只测自家页面，判据是你写的、页面是照判据写的，两者互相背书，你会看到一个满分或一个随你心情的分数。把工具指向别人的页面，它立刻抓出了别人（和你自己）看不见的失败项。

两个反直觉的发现：

- **工具在作者自己的页面上抓出了失败项**（主题簇内链数不足）。只测自家页面永远看不到这一项。
- **散文写得再扎实也判失败。** siwan.io 31 个段落、0 个列表项，同一把尺子下判失败；两个满分页的共性是表格化（93% / 40% 列表占比），不是篇幅长。把正文改表格不是美化——它改变了检索器能整块提取的内容。

## slint-community.mjs

对 Hacker News 做付费意愿信号的三闸门校验（换 2 个常量 + 1 个适配函数即可切到别的社区）。

| 闸门 | 做什么 | 拦住什么 |
|---|---|---|
| 1 Canary | 乱码串必须 0 命中 | 引擎没在做短语匹配时的假数字 |
| 2 精确短语 | 引号查询 + 逐页读到 EXHAUSTED | 松散匹配虚高 21 倍 |
| 3 修辞过滤 | 剔除 `if/but/although/though/wish` | 72.5% 的假买家信号 |
| 4 可交付物 | 须命中 dataset/api/csv/... | 泛泛抱怨，不描述「一个可做的东西」 |

```bash
node slint-community.mjs --days 30          # 默认 30 天窗口
node slint-community.mjs --days 7 --json    # 7 天窗口，输出 JSON 到 stdout
```

输出 `verifier-out/intent-report-{days}d.json`，含逐短语命中数、去重数、作者数、各闸门过滤量、可达性核验、以及通过全部闸门的候选全文（供人工逐条读——这一步不能省）。

**它不产出「需求强度」评分。** 它只告诉你哪些条目值得人工看。这个工具的价值在于让你**少信自己**。

## slint-page.mjs

8 项 AI 引用就绪度检查（判据来源见下表），逐项给出 pass / warn / fail 与依据。

```bash
node slint-page.mjs https://a.com https://b.com https://c.com
```

| # | 检查项 | 判据来源 |
|---|---|---|
| 1 | 正文服务端渲染（非 CSR 空 body） | arXiv 2510.11560 |
| 2 | 结构化数据（JSON-LD / microdata） | Writesonic 2026-07 |
| 3 | 内容可整块提取（列表/表格化） | Wellows 2026-07 |
| 4 | 精确数字 + 明确出处 | Ahrefs 12% |
| 5 | 主题簇内链 ≥ 3 | Writesonic 2026-07 |
| 6 | 绝对 URL canonical | Writesonic 2026-07 |
| 7 | 可见的更新时间 | Writesonic 2026-07 |
| 8 | robots.txt 未屏蔽主流 AI 爬虫 | arXiv 2510.11560 |

**刻意不打 llms.txt 分、不打排名分、不输出总分。** 原因：`llms.txt` 已被证伪（137k star 的域名实测 97% 零 AI 请求，且 Google 官方称其不影响排名）。单一「AI 可见度分数」是选层叙事。

**这个工具衡量的是页面自身条件，不是「是否真被引用」。** 就绪度是前提，不是结果。它无法证明任何引擎会引用你的页面——这需要引用面板凭据或实测流量数据。

## 边界与诚实声明

- 这两个工具**只能**证明「你看到的数字是不是真的」。它们不能替你判断一个需求值不值得做。
- 通过全部闸门的候选，**仍必须人工逐条读**。自动化只负责缩小范围，判断是人的事。
- `slint-community.mjs` 默认数据源是 HN Algolia 公共 API（免认证）。Reddit 的 OAuth 端点可达但需要自建应用凭据，网页路径在部分 IP 段被边缘拦截。
- 页面对比分数是**同一时刻**的快照，会随对方改版变化。

## 已知局限（用工具抓自己的错）

- `slint-page.mjs` 的 check 4 把 `warn` 和 `fail` 分开报，但 check 7 只要有任意日期串就算 pass——它分不清「2026-10-11 抓取」和「内容写于 2019 年」。这是已知的松判据。
- 移植网页版判据时曾漏掉对 `html === null` 的守卫，导致 3 处 regex 在取不到页面时崩溃。已补。**移植检查类代码时，原版的空值守卫要一起搬。**
